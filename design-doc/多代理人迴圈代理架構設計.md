# **迴圈代理與審查批評模式架構：多代理人系統中的記憶體隔離與上下文管理**

## **緒論與當代多代理人系統設計模式演進**

在當代人工智慧系統的發展軌跡中，基礎大型語言模型（Large Language Models, LLMs）的推理與生成能力雖然取得了長足的進步，但單一代理人（Single Agent）架構在處理高複雜度、長週期或需要嚴格品質控管的任務時，往往會遇到難以突破的能力瓶頸與邏輯死角。單一代理人系統通常依賴單一的人工智慧模型、一組預先定義的外部工具，以及一個綜合性的系統提示詞來自主處理使用者的請求 。在這種基礎模式中，代理人依賴模型的推理能力來解釋使用者的需求、規劃多個步驟的序列，並決定要使用哪些工具 。然而，這類架構在需要高度自我修正、深度邏輯推理以及避免幻覺的場景中，容易陷入模型固有的自回歸局限性。為了解決這些單點失效的問題，多代理人模式（Multi-Agent Pattern）應運而生，其核心精神在於透過代理人的專業分工、平行處理能力與互相制衡，來協調多個代理人共同完成極度複雜的任務 。  
在產業界與學術界廣泛探討的代理人設計模式中，主要包含了反思模式（Reflection Pattern）、工具使用模式（Tool Use Pattern）、規劃模式（Planning Pattern）以及多代理人協作模式 。其中，反思模式賦予了代理人內省並評估其行動或決策的能力，強調透過反覆運算來改善結果，而不僅僅是單向地執行任務 。當我們將這種反思機制進一步升級，並將其角色拆分給不同的代理人實體時，便構成了審查與批評模式（Review and Critique Pattern），亦被稱為生成器與批評者模式（Generator and Critic Pattern）或迴圈代理模式（Loop Agent Pattern） 。這種模式被證明是提升生成內容品質與可靠性的最佳架構實踐之一，特別適用於需要高度精確性的場景，如程式碼撰寫、法律合約審查或高風險的商業報告生成 。  
審查與批評模式通常在一個序列化或迴圈的工作流程中運作，由兩個或多個具備高度專業化的代理人組成。生成器代理人（Generator Agent）負責創建初始的輸出草稿，隨後，批評者代理人（Critic Agent）會根據一組預先定義的嚴格標準（例如事實準確性、格式合規性或內部邏輯一致性）對該輸出進行全面的評估與審查 。這種架構不僅能捕捉單次生成中容易遺漏的錯誤，更能透過迭代精煉（Iterative Refinement）的過程，大幅提高最終輸出的精確度 。在這種生成、批評、再生成的循環中，迴圈會在達到預設的品質閾值或是達到最大迭代次數時終止 。  
當系統架構設計師試圖在一個 Python 運行環境（Runtime）中實作兩個基於 ReAct（Reasoning and Acting）框架的代理人，並使它們在迴圈中相互拮抗（Antagonize）時，系統底層的資料流複雜度會呈指數級上升。ReAct 代理人的運作機制強烈依賴於持續將自身的推理軌跡（Reasoning Traces）與外部工具的調用結果寫入上下文記憶中，這賦予了模型強大的推理與解釋能力 。然而，若生成器與批評者在 Python 記憶體中共享同一個上下文物件指標（Context Object Pointer），或者系統的上下文管理器未能有效在邏輯與物理層面隔離雙方的思考過程，便會引發嚴重的記憶體錯亂、變數覆寫與資訊串擾現象 。為確保兩個 ReAct 迴圈能在相互拮抗的過程中保持邏輯清晰，且不會因為看到對方的內部糾結而產生幻覺，開發者必須在整個 Python 運行時期中維護兩套獨立的 ReAct 迴圈實例、對應的多層次記憶體儲存體（Memory Store），以及具備嚴格存取控制的精細上下文管理器。

## **ReAct 框架的本質與確認偏誤陷阱**

要深刻理解為什麼需要將生成與批評分離為兩個獨立的 ReAct 迴圈，以及為什麼記憶體隔離如此關鍵，必須先回顧 ReAct 框架的運作本質以及大型語言模型在自回歸生成中的內在缺陷。ReAct 框架的核心思想是將語言模型的「推理（Reasoning）」與「行動（Acting）」交織在一起。在每一次迭代中，代理人會先生成一段內部思考（Thought），藉此分析當前狀態並決定下一步的行動；接著，代理人會生成行動指令（Action）以呼叫外部工具；最後，工具的回傳結果會作為觀察（Observation）附加到上下文中 。這種「思考-行動-觀察」的顯式推理軌跡不僅是模型解決複雜問題的階梯，本身也會成為後續推理的上下文輸入 。  
這種機制的優勢在於高度的透明性與可解釋性，但同時也引入了龐大且持續累積的上下文負擔。在真實世界的應用場景中，來自外部工具的輸出（例如網頁搜尋的原始 HTML 內容、龐大的資料庫查詢回傳結果）會使上下文長度急遽膨脹 。Anthropic 的研究指出，多代理人系統在平行運作並維護各自上下文時，其 Token 的消耗量可能高達一般聊天應用的 15 倍 。如果系統架構將所有這些冗長且充滿雜訊的推理軌跡與觀察結果不加區分地寫入同一個共享記憶體池（Shared Pool），並對所有的代理人可見，不僅會造成 Token 資源的極大浪費，更會引發嚴重的資料一致性衝突 。  
更深層的技術挑戰在於語言模型的「確認偏誤（Confirmation Bias）」。當一個單一模型試圖評估自己剛剛生成的內容時，其初始的輸出路徑與思維軌跡會強烈影響後續的推理生成。由於模型是基於先前生成的 Token 來預測下一個 Token，因此它極難跳脫自己預設的邏輯框架去發現自身所犯下的錯誤 。近期的代理人記憶體研究論文強烈主張，單一模型同時生成解決方案、批評該解決方案並規劃下一次嘗試，這三種角色本質上會相互干擾，因此必須將這三種功能在架構上徹底分離 。這正是將單一代理人拆分為生成器、批評者甚至是驗證者（Verifier）的根本原因 。這種角色分離的設計強制在生成與評估之間建立物理或邏輯上的屏障，從而提高回饋的客觀品質並大幅降低自我確認偏誤 。  
然而，如果我們在 Python 架構層面沒有落實絕對的記憶體隔離，這種角色分離便形同虛設，且會產生「上下文污染（Context Pollution）」。在 Python 運行時中，如果生成器代理人 A 與批評者代理人 B 的對話歷史是透過共享同一個 List 或 Dict 物件來傳遞，代理人 B 將能夠在上下文中看到代理人 A 產生初始草稿時的完整內部推理過程、失敗的工具調用紀錄與錯誤嘗試。這種敏感上下文的暴露會徹底破壞代理人 B 作為客觀批評者的獨立性，甚至可能導致代理人 B 的內部狀態被代理人 A 的錯誤推理所「同化」或誤導。反之亦然，如果代理人 A 在後續的生成迴圈中看到了代理人 B 思考如何進行嚴厲批評的內部自言自語，可能會在其後續的生成中產生行為混亂或過度修正。因此，確保每個代理人實例的記憶體空間與上下文生命週期完全獨立，是多代理人架構設計的絕對先決條件 。

## **審查與批評模式的拮抗迴圈設計與機制**

審查與批評模式的核心在於建立一個高度專業化且穩健的反饋迴圈（Feedback Loop），這個過程在系統架構中經常被稱為生成器與批評者（Generator-Critic）模式 。為了使這種對抗機制（Antagonism）發揮最大效用，批評者代理人的設計必須建立在明確的評估基準（Rubric）與結構化的回饋通道之上。  
當批評具備高度專業化時，此模式的效益最為顯著。以軟體工程領域為例，一個負責程式碼審查的批評者代理人可以被設定為專注於尋找邏輯錯誤（Bugs）、邊界情況（Edge Cases）或是潛在的安全漏洞（Security Vulnerabilities）；而在商業領域中，一個負責合約審查的批評者則可以專注於檢查缺失的法律條款或商業邏輯上的矛盾 。在某些涉及視覺輸出的應用中，例如生成網頁或 PDF 文件，甚至可以採用進階的「渲染-截圖-批評（Render-Screenshot-Critique）」變體，讓視覺語言模型作為批評者來評估最終的視覺呈現 。  
在更高階且高風險的工作流程中，單一的批評者往往不足以應付所有潛在的品質缺陷。此時，系統設計者會採用平行化的多重批評機制，即平行運行多個高度專業化的批評者，每個批評者專注於不同的品質維度。

| 批評者類型 | 主要評估維度與職責 | 判定依據與工具授權 |
| :---- | :---- | :---- |
| **事實準確性批評者** | 檢查生成內容中的聲明、數據與事實是否與來源文件或外部知識庫完全一致 | 具備檢索增強生成 (RAG) 能力，可存取原始知識庫或呼叫網頁搜尋工具進行交叉比對。 |
| **格式與結構批評者** | 驗證輸出是否符合嚴格的結構描述 (Schema) 或特定的文件排版規範 | 利用正則表達式 (Regex) 或 JSON Schema 驗證工具輔助判斷。 |
| **語氣與風格批評者** | 評估遣詞用字是否符合目標受眾的適當性（如過於正式、過於隨便或過於冗長） | 依賴特定的系統提示詞矩陣，定義品牌風格指南或受眾輪廓。 |
| **完整性批評者** | 檢查所有必要的問題是否都被回答，所有必填欄位或章節是否存在 | 將任務的原始需求清單與生成內容進行逐項映射比對。 |

在建立這種拮抗迴圈時，開發者必須遵循幾個嚴謹的設計步驟。首先，必須明確定義生成步驟（Generation Step），這是代理人被建立的主要任務，其輸出將成為「候選結果（Candidate Result）」 。這時候，生成器代理人應該專注於產出，不需要（也不應該）在其提示詞中過度融入自我 QA 的邏輯，而是將品質控管的責任完全轉移給外部的包裝層，即批評者 。  
其次，必須為批評者提供嚴格的評估標準（Evaluation Criteria）。批評者需要確切知道「良好」的定義為何，這通常透過獨立的提示詞（Prompt Matrix）來規範 。為了確保批評的有效性，批評者必須能夠存取生成器所使用的相同來源材料，並且被明確指示將生成的輸出與來源材料進行客觀比對，而非在孤立的狀態下僅憑常識進行評估 。  
在實作層面，建立批評者代理人的系統提示詞應當與生成器完全隔離。這個獨立的提示詞應包含四個核心區塊：原始任務的用戶指令、生成器產出的候選輸出（通常作為動態變數注入）、格式清晰且無歧義的評估標準，以及要求返回結構化回饋的強硬指令 。一個優良的批評者輸出必須是易於 Python 程式碼解析的格式，例如一個 JSON 物件，其中應包含布林值（例如 passed: true/false）、發現的具體問題陣列（issues: \[...\]），以及建設性的修訂建議（revision\_notes: "..."） 。這種結構化的輸出是確保下游編排層的條件路由邏輯（Conditional Branching Logic）能可靠運作的關鍵，只有當 passed 為真時，迴圈才會終止並輸出最終結果。

## **記憶體空間的物理與邏輯隔離機制**

在 Python 運行環境中實現前述的拮抗迴圈，最艱鉅的工程挑戰在於如何徹底隔離兩個 ReAct 代理人的記憶體空間。Python 語言的特性在處理可變物件（Mutable Objects，如 list 與 dict）時是採用傳址參考（Pass by Reference），這意味著如果系統開發者只是簡單地將一個對話歷史清單（Message List）在不同的代理人函數之間傳遞，所有的代理人實際上都在讀寫同一個記憶體區塊。  
為了從根本上解決這個問題，開發者必須採用先進的狀態管理與上下文隔離技術。在此領域中，目前業界領先的開源編排框架如 LangGraph、Mastra 以及 Google Agent Development Kit (ADK) 皆提供了各具特色且強大的解決方案。

### **基於子圖架構的狀態隔離技術**

在處理多代理人記憶體管理時，將複雜任務拆解為獨立的狀態圖（State Graph）是目前最被推崇的最佳實踐。以 LangGraph 的架構思維為例，其提供了一種極為優雅且嚴密的狀態隔離機制——子圖（Subgraphs）。在 LangGraph 的設計中，子圖的狀態可以完全獨立於父圖（Parent Graph）的狀態而存在 。這意味著兩個圖可以完全孤立地運作，沒有任何直接的共享狀態或對特定狀態鍵值（State Keys）的隱式依賴 。  
在這樣的架構下，父圖與子圖之間可能不存在任何重疊的狀態變數。因此，系統必須在父圖調用子圖之前進行「狀態轉換（State Transformation）」過程，也就是說，輸入的資料在傳遞給子圖之前必須被重新映射或過濾，並在子圖完成運算返回結果後，將其輸出轉換回父圖預期的格式 。這種轉換過程充當了隔離連接器的角色，允許獨立的組件在不修改其內部結構或破壞命名空間的情況下進行安全的互動 。  
對於生成器與批評者模式而言，這表示生成器與批評者可以被封裝為兩個完全獨立的子圖。每個子圖擁有自己私有的 TypedDict 作為狀態定義。生成器在其私有狀態中擁有一個用來記錄與 LLM 互動的 messages 陣列，批評者同樣擁有自己的 messages 陣列。由於這種物理與邏輯的隔離，生成器內部的推理鍵值永遠不會污染父圖的狀態命名空間，更不可能被批評者讀取到 。如果缺乏這種基於 TypedDict 與轉換層的隔離機制，子圖內部的過渡性對話訊息將會在父圖中不斷累積，最終破壞主對話歷史的純潔性，並導致 LLM 遇到 Token 上限錯誤 。  
這種模組化的思維類似於將大型 Python 程式分解為擁有私有變數的獨立類別與函數：隱藏內部的複雜度與中間運算過程，僅向外部暴露乾淨的介面與最終結果 。

### **基於訊息過濾與委派的記憶體範圍控制**

另一種確保記憶體隔離的策略是基於訊息過濾與動態範圍限制的委派機制，此理念在 Mastra 等多代理人框架中得到了良好的體現。在主管代理人（Supervisor Agent）負責協調多個專業子代理人的模式中，主管可以根據任務的進度將特定的工作委派給子代理人 。  
為了在這種動態委派中實現記憶體隔離，Mastra 實施了精細的上下文轉發機制。當主管委派任務時，子代理人會收到包含完整歷史脈絡的對話上下文，以確保其具備足夠的全局資訊進行高質量的決策；但至關重要的是，這種讀取權限是單向且唯讀的。系統只會將該子代理人專屬的委派提示詞以及其最終的生成回應儲存到該子代理人的私有記憶體中 。  
每次的任務委派都會自動產生並使用一個全新的執行緒識別碼（Thread ID），確保了每一次獨立互動在資料庫層面的乾淨分離 。這種「讀取全局，寫入局部」的嚴格策略，既保證了生成器與批評者在執行任務時能獲得充分的背景知識，又絕對防止了各自的內部推理軌跡在會話狀態（Session State）中相互交織與污染。結合工作流程與記憶體管理，可以實作完美的交接模式（Handoff Pattern），讓控制權在生成器與批評者之間清晰地轉移，而不會留下混亂的對話殘留 。  
類似的架構也在開源專案 OpenClaw 中被提出，用以解決多代理人系統的資源消耗與狀態污染問題。傳統的架構可能要求為每個代理人啟動一個獨立的網關進程（Gateway Process），這會消耗龐大的系統記憶體資源 。而更先進的做法是運行一個單一的守護進程（Daemon），該進程擁有所有的狀態連接，但其內部的每個代理人（如生成器與批評者）都被分配到完全隔離的工作空間（Workspace），擁有獨立的記憶體文件、狀態文件與對話群組拓樸 。除非透過明確配置的共享路徑，否則代理人 A 的記憶體對代理人 B 永遠是不可見的，這實現了資源效率與狀態純潔性的完美平衡 。

### **向量情節記憶庫的深度整合**

在長週期的拮抗代理人運作中，僅依靠短期記憶內（In-memory）的上下文視窗是遠遠不夠的。傳統的基於先進先出（FIFO）或近期性（Recency-based）的緩衝記憶體在處理龐大且複雜的推理任務時，極易將早期的關鍵資訊移出上下文視窗而導致失憶 。為了解決這個問題並強化代理人的長期學習與糾錯能力，先進的系統架構應整合「向量情節記憶（Vector Episodic Memory）」作為傳統文字緩衝區的替代方案。  
這種記憶體設計的核心機制是將代理人過去的「反思（Reflections）」、失敗的嘗試，或者是批評者過去給出的嚴厲回饋，透過嵌入模型轉換為密集向量（Dense Embeddings）並儲存至向量資料庫中 。當生成器或批評者在後續的迭代中遇到類似的任務或程式碼區塊時，系統會根據當前任務的語義相似度（Semantic Similarity），從資料庫中精準檢索出相關的歷史記憶 。  
在生成器與批評者對抗的架構中，向量記憶的應用場景極為廣泛。批評者可以從向量記憶庫中檢索過去對類似程式碼錯誤的批評記錄，從而提供更具一致性、深度與權威性的反饋，這在評估長篇距（Long-Horizon）任務時尤為重要 ；而生成器也能透過檢索機制，回憶起過去被批評者糾正的血淚經驗，主動在本次生成中避開類似的陷阱，避免在同一個問題上重蹈覆轍。這種基於語義相似度檢索而非單純依賴線性對話歷史堆疊的記憶管理方式，與新興的認知代理人架構趨勢高度一致，能夠顯著提升系統在長時程任務中的穩健性與適應能力 。  
為了清晰展示不同層級記憶體在 Python 運行時期的管理方式與技術選型，以下提供架構設計的多維度記憶體分層矩陣：

| 記憶體層級 (Memory Layer) | 儲存載體與底層技術 | 生命週期與持續性特徵 | 代理人隔離策略與實作機制 | 應用於生成器/批評者迴圈之具體目的 |
| :---- | :---- | :---- | :---- | :---- |
| **短期工作記憶 (Working Memory)** | 記憶體內變數 (如 Python TypedDict, Pydantic Models) | 短暫，與單次 ReAct 執行緒或子圖生命週期嚴格綁定，執行完畢即垃圾回收 (GC)。 | 透過變數作用域 (Scope) 與子圖命名空間進行物理隔離。父圖與子圖必須透過顯式的轉換函數交換狀態 。 | 儲存生成器的即時推理軌跡 (Thoughts/Actions)、龐大的外部工具調用原始輸出。批評者**絕對不可見**生成器的此層記憶。 |

## **當代多代理人編排框架之架構比較與技術借鑑**

要在 Python 運行時期中同時維護兩個相互拮抗且狀態隔離的 ReAct 迴圈，開發者面臨著極度精確的工作流程編排與狀態流轉控制挑戰。如果試圖手動透過 Python 的非同步函數（asyncio）、全域變數與複雜的 while 迴圈來硬編碼這些邏輯，將會迅速失去對系統可觀察性（Observability）、可恢復性（Resumability）的掌控，並且極易產生難以追蹤除錯的無窮迴圈或死結 。因此，必須依賴具備圖形化執行引擎（Graph-based Execution Engine）或狀態機概念的現代化代理人編排框架。  
以下將深入探討並比較 Google Agent Development Kit (ADK) 與 LangChain 體系的 LangGraph，分析它們在處理迴圈、異常中斷與人類介入方面的進階機制，為架構設計提供技術藍圖。

### **Google Agent Development Kit (ADK) 及其進階工作流程機制**

Google ADK 是一個具備極高靈活性的開源代理人開發框架，特別擅長處理確定性的執行流程。在 ADK 2.0 版本中，它引入了基於圖形的執行引擎（Workflow Runtime），用以組合代理人應用的確定性執行流，支援路由、迴圈、重試、狀態管理與人類在環（Human-in-the-loop）等複雜模式 。  
在 ADK 的架構中，LoopAgent 是一個極為強大的模板化工作流程代理人，專門用於在迴圈中執行其下屬的子代理人陣列，直到滿足特定的終止條件或達到預設的最大迭代次數（max\_iterations） 。這非常適合用於實作需要不斷重複精煉的場景，例如程式碼優化或文件的生成與審查 。  
在 ADK 中實作生成器與批評者的拮抗迴圈時，LoopAgent 對於子代理人的調度順序是確定性的（Deterministic），而非由語言模型的幻覺來隨機決定 。這意味著編排層（Orchestration Layer）的執行邏輯被穩固地固定下來，保證了每次迭代中必定是：生成器先產出，批評者再接手進行評估 。這種確定性極大地降低了系統除錯的難度。  
然而，在迴圈控制上，挑戰在於如何優雅且精準地中斷迴圈。傳統上，如果批評者認為輸出已經達到完美標準，不需要再繼續迭代，它可以透過呼叫一個帶有 tool\_context.actions.escalate \= True 屬性的工具來觸發退出訊號 。但是，這種全局的升級（Escalate）訊號會一路向外傳遞，導致包含該迴圈的父級序列代理人（SequentialAgent）也隨之崩潰或中止，使得迴圈之後的後續步驟無法執行，這在生產環境的複雜嵌套工作流程中是無法接受的 。  
為了解決這個控制流問題，ADK 的進階設計在社群的推動下引入了 EscalationContext 機制。透過在工具上下文中設置 tool\_context.actions.escalation\_context \= EscalationContext(type='parent')，批評者代理人可以精準地指示系統僅退出當前最鄰近的這層子迴圈（例如僅結束生成器與批評者的反覆運算），而讓外層的父級工作流程得以無縫接軌並繼續執行下一步驟（例如將最終結果交給下一個發佈代理人） 。另一種提出的架構解法是在定義 LoopAgent 時，直接配置 halt\_on\_escalate=True 的參數，使得該迴圈在收到內部子代理人的中斷訊號時，能夠自行吸收該訊號並正常結束，而不會將錯誤往上拋出 。這種具有層級意識與細粒度控制的異常流機制，是確保複雜巢狀多代理人系統穩定運行的核心關鍵。

### **LangGraph 的檢查點持久化與暫停恢復機制**

若選擇採用 LangGraph 來建構這個 Python 運行時期架構，則記憶體管理與拮抗迴圈控制的核心將高度依賴於其強大的 Checkpointer 系統與 StateGraph API。LangGraph 的設計哲學將代理人的互動視為有向圖（Directed Graph）上的節點跳躍。它會在圖形執行的每一個有意義的步驟自動儲存完整的狀態快照（State Snapshot），這使得代理人的執行軌跡得以被完美記錄、除錯，甚至支援時光倒流般的重放機制。  
在建立生成器（封裝為子圖 A）與批評者（封裝為子圖 B）時，它們都作為獨立的節點被嵌入到一個主迴圈圖（Parent Graph）中。當生成器完成其繁重的 ReAct 迴圈並最終產出草稿後，它會透過一個狀態映射函數（State Mapping Function）將這份「純淨」的最終草稿更新回父圖的狀態字典中。接著，圖形的邊緣（Edge）會將執行流導向批評者節點。批評者節點被喚醒後，它只讀取父狀態中的這份草稿，結合自身的私有提示詞與儲存於向量資料庫的評估標準，展開另一個完全獨立的推理與查證過程。如果批評者判定草稿未達標，它會將包含明確錯誤指引的修訂意見寫回父狀態，接著條件路由函數（Conditional Routing Function）會根據這份狀態中的布林值，將控制權重新拉回生成器節點，形成封閉的拮抗迴圈。  
為了防止這種嚴格的拮抗過程因為生成器能力不足而陷入無止境的無窮迴圈，消耗巨額 API 成本，系統必須在父圖的狀態中維護一個迭代計數器（Iteration Counter） 。每次經過批評者節點後，條件邊緣會檢查：(1) 批評者是否給出了通過（passed: True）的標記；(2) 迴圈計數是否已經達到預設的上限。若達到上限但仍未獲通過，系統必須具備降級處理機制（Fallback Mechanism）或進入人工介入流程 。  
在許多高風險或具有法律、財務影響的決策環節中，引入人類在環（Human-in-the-Loop, HITL）是確保系統安全與最終責任歸屬的重要防線 。在 LangGraph 中，開發者可以利用強大的 interrupt() 原語。這個函數能在圖形到達特定節點（例如批評者依然不滿意，但次數已達上限時）優雅地暫停整個圖形的非同步執行，並將目前的狀態有效負載（Payload）推播給前端介面供人類審查者查看 。在暫停期間，所有的狀態與對話歷史都安全地凍結在 PostgreSQL 支援的檢查點資料庫中 。當人類審查者給出具體回饋或強制批准後，系統會接收到 Command(resume=...) 指令，圖形便會準確地從當初停止的節點恢復執行，並將人類的回應無縫注入上下文狀態中繼續後續流程 。同樣的防護理念在 ADK 中，則可以透過實作一個特定的 ApprovalTool 代理人來達成，該代理人會主動暫停執行流，等待外部系統觸發人類的「是」或「否」批准訊號後才放行 。

## **最適化 Python 運行時雙 ReAct 迴圈架構圖與組件設計**

綜合前述對記憶體隔離的迫切需求以及現代編排框架的技術優勢，為了解決單一 Python 運行時期中龐大上下文造成的記憶體膨脹，確保生成器與批評者之間具備極致的邏輯隔離，本報告提出一套「**解耦式多代理人狀態機架構（Decoupled Multi-Agent State Machine Architecture）**」。  
此架構的核心設計哲學在於：**將大語言模型的推論運算層（GPU-bound）與代理人的工作流程編排與記憶體管理層（CPU-bound）徹底分離** 。在這種現代化設計下，Python 運行時期的主程式並不負責持有所有臃腫的模型互動狀態，而是化身為一個輕量級的高效編排器（Orchestrator），專注於狀態圖的流轉控制、檢查點的讀寫以及子代理人 API 的調度。

### **核心組件設計規範**

為了支撐這個架構，系統必須實作以下四個核心組件層：

1. **編排與路由層 (Orchestration Engine)：** 負責維護主迴圈的最高階狀態邏輯，並控制訊息在生成器與批評者之間的精確傳遞。此層必須強制實現狀態轉換函數（State Transformation Functions），確保批評者被喚醒時，只接收到生成器產出的純粹文字草稿以及相關的評估標準，而絕對無法透過物件參考存取到生成器的工具調用歷史與複雜的內部思維軌跡。同時，它也負責監控防護機制，如迭代次數上限與超時控制 。  
2. **記憶體隔離牆 (Memory Isolation Boundary)：** 在運行時期中為每個啟動的代理人實例配置獨立的上下文物件與命名空間。當執行權限移轉時，系統透過深拷貝（Deep Copy）或序列化為 JSON 後再反序列化的嚴格 Schema 轉換來傳遞必要數據，這能從底層徹底斬斷 Python 中危險的物件參考共享（Reference Sharing）問題。  
3. **持久化儲存後端 (Persistence Backend)：** 為了支援長週期的非同步任務與人類介入暫停，系統必須整合如 PostgreSQL 的關聯式資料庫作為 Checkpointer 的底層後端 。這使得每一次代理人的狀態變更都能安全寫入硬碟落地。這不僅解決了 RAM 記憶體溢出的問題，更賦予了系統在發生崩潰後自動恢復（Crash Recovery）以及支援時間旅行除錯（Time-travel Debugging）的高階能力。  
4. **動態工具集與向量反思庫 (Dynamic Toolset & Vector Reflection Store)：** 作為批評者的專屬火力展示區。此層包含用於格式驗證的正則表達式引擎、用於結構驗證的 Pydantic 模型驗證器，以及用於檢索歷史錯誤樣態與成功修正經驗的向量資料庫，藉此大幅提升批評者在長時間運作下評估標準的一致性。

### **系統架構圖 (System Architecture Diagram)**

為了清晰具現化上述的設計邏輯與資料流動方向，以下提供基於嚴格隔離原則繪製的最佳化系統架構圖。該架構展示了父級控制器如何安全地調度兩個獨立的 ReAct 子系統，並透過隔離的記憶體空間與持久化檢查點機制進行拮抗式的資料交換。

在此解耦架構中，「狀態轉換屏障（State Filter）」扮演了整個系統穩定性的絕對守門員角色。當父控制器準備喚醒生成器子系統時，過濾器會將父狀態中的全局資訊進行精煉提取，僅擷取最原始的任務描述以及上一輪批評者給出的「具體修正意見清單（Issues）」。更重要的是，過濾器會強行阻斷並屏蔽批評者在查閱文件、提取證據時的那些囉嗦且充滿干擾的內部 ReAct 對話紀錄。  
同樣的防護機制也應用於批評者端。當喚醒批評者子系統時，狀態轉換屏障只會傳入生成器產出的「最終乾淨草稿」，徹底抹除生成器在構思這份草稿時，可能因為幻覺而失敗呼叫搜尋引擎，或是反覆修改程式碼報錯的冗長內部崩潰日誌。  
這種屏障設計不僅實現了記憶體空間與上下文狀態的完美物理隔離，從根本上消滅了大型語言模型的確認偏誤與上下文污染；它更帶來了一個極具價值的附帶效益：大幅減少了每次呼叫 LLM 推論引擎時需要傳輸的 Token 數量。透過剔除與該階段任務無關的歷史雜訊，系統能夠有效降低雲端 API 的呼叫成本與推理延遲。透過將每個代理人的複雜內部推理侷限在自身的子圖（Subgraph）生命週期內，並在子圖結束時任由其龐大的私有狀態被垃圾回收機制消滅（或僅留存於供離線除錯使用的 Checkpointer 歷史深處），Python 運行環境便能在極低的記憶體負擔與最高層級的邏輯穩定度下，長期維繫兩個強大 ReAct 迴圈的拮抗與協作運作。

## **進階運行時陷阱與防護機制：失憶症與對話式前言**

在實作解耦式多代理人狀態機時，雖然實體記憶體隔離能有效防止上下文污染，但也引入了兩個在大型語言模型實際運行時極易發生的致命陷阱：**生成器失憶症（Generator Amnesia / Brain Split）**與**對話式前言混亂（Conversational Preamble Chaos）**。系統必須在提示詞與狀態流轉層面建立針對性的防護。

### **1. 生成器失憶症（Generator Amnesia / Brain Split）**

**問題成因：** 為了徹底隔離，系統會在每次迭代時重置生成器的 `AgentSession`。當批評者在第一輪給出「第二段缺乏數據支持」的修改意見時，生成器在第二輪啟動時會收到該意見，但卻**遺忘了自己原本寫的第一版草稿**。這導致生成器被迫從零開始重寫，引發嚴重的輸出不穩定與無限迴圈（Chaos Interaction）。

**架構解法：** 狀態過濾器（State Filter）必須在派發修改任務時，將前一輪的候選草稿（Previous Draft）作為「唯讀上下文」重新注入生成器的初始提示詞中（例如使用 `━━━ YOUR PREVIOUS DRAFT ━━━` 標籤）。如此一來，生成器便能準確地針對原有內容進行局部修正，在維持 ReAct 軌跡隔離的前提下，徹底解決腦裂與失憶問題。

### **2. 對話式前言混亂（Conversational Preamble Chaos）**

**問題成因：** 語言模型具有強烈的對話傾向。在修正草稿後，生成器往往會輸出類似「*我已經根據您的建議修改了第二段，以下是新的草稿：*」的閒聊前言。由於編排器會盲目地將生成器的**全部輸出**作為純淨草稿傳遞給批評者，批評者在評估時會看到這些非專業的對話內容，從而判定草稿不合格，導致迴圈卡死。

**架構解法：** 必須在生成器的系統提示詞（System Prompt）中，加入強制的**純淨輸出指令（Critical Output Rule）**，明確禁止任何元對話（Meta-commentary）或包裝詞。確保生成器的輸出 100% 僅包含任務要求的草稿本文，從而將代理人之間的互動嚴格限制在可控的領域範疇內。

## **結論與系統未來展望**

在建構需要自我修正、深度迭代且品質要求極高的人工智慧應用時，單純依賴單一代理人的自我反思能力，往往會受制於底層語言模型自帶的確認偏誤與視野盲區。採用生成器與批評者（Review and Critique）的多代理人模式，透過強制性的專業角色分離與嚴格的相互拮抗機制，能夠有效突破此一技術瓶頸，達到人類專家級別的審閱品質。然而，此架構模式的成敗，完全取決於系統開發者對於 Python 運行環境底層的「記憶體隔離」與「動態上下文管理」的掌控精確度。  
本研究報告深入探討了在單一 Python 運行時期中實作雙 ReAct 迴圈架構的各項技術挑戰與最佳實踐方案。深度分析表明，將所有代理人的推理思維軌跡與龐大的外部工具回傳結果不加區分地混合於同一共享記憶體池中，是導致跨使用者污染（UCC）、邏輯同化現象以及系統記憶體崩潰的罪魁禍首。為了解決這個致命的設計缺陷，系統架構設計師必須揚棄傳統共享狀態的迷思，全面轉向採用具備高內聚、低耦合特性的「解耦式多代理人狀態機架構」。  
在此提出的最佳化架構中，開發者應積極導入並善用現代化編排框架的特性，如 LangGraph 提供的子圖私有狀態（Private TypedDict）機制，或是 Google ADK 2.0 提供的層級化範圍控制升級機制（EscalationContext），藉此為每個代理人建立絕對獨立且短暫的工作記憶體空間。同時，透過在系統的編排路由層引入嚴格的狀態轉換過濾器（State Filter），確保生成器與批評者這兩個拮抗角色，僅能透過高度結構化（如 JSON Schema 約束）的最終產出進行受控通訊，從而徹底斬斷內部推理軌跡交叉污染的可能性。  
此外，為了賦予系統在長時程與高複雜度任務中的極致穩定性，必須將大模型的推論層與代理人的工作流程編排層進行物理與邏輯上的雙重解耦，並利用如 PostgreSQL 的企業級持久化儲存方案來管理圖形的檢查點狀態，甚至預留人類在環（Human-in-the-Loop）的防護機制介入點。唯有透過這套結合了嚴格狀態機路由、精細上下文屏障過濾、持久化隔離記憶體，以及向量情節記憶檢索的全面性系統設計，開發者才能在單一 Python 運行環境中，成功且穩健地駕馭多個 ReAct 迴圈的拮抗協作。這將是通往打造具備企業級可靠性、可擴展性與極致輸出品質的自主人工智慧代理系統的必經之路。
